# 사용자 결정과 변경 이력

결정은 기록된 선택의 관계이며 사실 검증 결과가 아니다. 사용자 발언의 인용·출처도
AI가 제공한 정보다. 사용자 인증이나 전자 서명으로 표시하지 않으며 모든 조회의
`claims_verified`는 false다. 기존 자유 문장 기록을 추정해서 분류하지 않는다.

## 저장과 판정

기존 `memory_checkpoint`의 `kind: decision`에 선택적인 `decision` 정보를 전달한다.
`body`는 원문이며 `report`는 기존 사람용 요약이다. v13 `decision_events`에는
연결 정보만 추가한다. 원문·기존 report JSON·이전 행을 수정하지 않는다.
원문·연결·영수증은 프로젝트 revision 검사와 같은 트랜잭션으로 저장한다.

범위는 프로젝트·저장소·환경·주제 키·명시적 구성요소·명시적 기능의 조합이다.
생략한 구성요소/기능은 서비스 공통이며, 기록 제목이나 경로에서 추측하지 않는다.
구성요소·기능을 지정하려면 먼저 해당 작업에 연결해야 한다.

| 행동 | 의미 |
|---|---|
| `decide` | 새 선택. 다른 선택이 남아 있으면 충돌로 유지 |
| `replace` | 명시한 현재 선택들을 정정. 이전 원문은 보존 |
| `withdraw` | 명시한 현재 선택들을 철회. 이전 조상을 되살리지 않음 |
| `propose` | AI 제안. 현재 선택을 바꾸지 않음 |

`choice_key`는 AI가 명시한 선택 구분자다. 서로 다른 활성 키가 있으면 충돌이다.
문장의 의미가 같은지·반대인지 자동 분석하지 않는다. 같은 키라고 정확성이 검증되는
것도 아니다. `source.kind=user_statement`와 contemporaneous인 기록만 현재 관계를
변경할 수 있다. 소급·시점 미지정 기록은 이력으로만 남으며 정정·철회할 수 없다.

주제 상세에서 받은 **전체** `active_record_ids`를 `expected_current_ids`에 넣는다.
빈 배열은 첫 결정 또는 현재 선택이 없는 상태를 뜻한다. 변경되면 저장을 거절한다.
`targets`에는 같은 범위에서 아직 활성인 ID만 넣는다. 중복·다른 주제·다른 범위·미래
기록을 거절한다. 일반 `supersedes`로 구조화 결정을 우회해서 바꾸지 못한다.

## 조회와 화면

`memory_query_decisions`와 인증된 GET `/api/decisions`는 같은 읽기 모듈을 사용한다.
화면 상단 **결정·이력**에서 서비스별 주제, 현재 선택, 충돌, 정정 전 선택과 철회
흐름을 본다. 출처를 펼치면 인용·참조·원문 기록 ID·작업 ID를 볼 수 있다.
긴 원문은 일부만 표시하고 원문 조회 방법을 안내한다. 일반 작업 조회의 결정 기록은
과거 자료일 수 있으므로 최신 문장만으로 현재 결정을 판단하지 않는다.

카탈로그는 최신 활동순 12개씩, 상세는 최근 20개 이력을 바이트 상한 안에서 표시한다. `history_next_offset`을 `history_offset`으로 넘겨 이전 이력을 조회한다. 공통 구성요소·기능의 정확한 필터는 빈 문자열이다. 생략하면 모든 범위를 조회한다. 전체 판정은 주제별
최대 200건으로 제한한다. 이 한도를 넘은 기존 자료는 미확인으로 표시하며 불완전한
활성 ID를 저장 기준으로 제공하지 않는다. 200건인 주제에 새 변경 저장은 거절한다.
기록 삭제나 자동 주제 분할은 하지 않는다. 큰 주제의 분할 정책은 별도 후속 작업이다.

## 호환과 검증

v1–v12 DB는 읽기 전용 화면에서 유지되며 결정 연결 조회는 미지원으로 표시한다.
새 쓰기 연결은 v14까지 추가 마이그레이션한다. v13은 연결 테이블, v14는 구버전 writer도 원문을 변경하지 못하게 하는 DB 보호 규칙이다. 구버전 실행 파일로 새 DB를 열지 말고
화면·MCP·유지보수 도구를 함께 갱신한다. 실행 중인 구버전 reader가 새 DB를 지원한다고
추정하지 않는다. 전체 백업·복원과 프로젝트 사본 교환은 결정 정보와 ID를 보존하고,
가져오기 시 선택 관계·출처·대상·범위·순서를 다시 검사한다. 가져온 보고를 인증하지 않는다.

저장 실패는 기존 checkpoint 복구 절차를 사용한다. 충돌·잘못된 대상은 자동 재작성하지
않는다. 원래 요청이 실제 보관됐는지 확인하고 같은 키·입력으로만 허용 범위에서 재시도한다.
