# 로컬 백업·복원과 프로젝트 사본 이동

현재 구현은 **로컬 파일을 새 폴더에 복사하는 유지보수 명령**이다. 별도 서버나 AI를
실행하지 않으며 네트워크로 보내지 않는다. 기존 DB, 기록, 설정, 스킬, 연결은 변경하지 않는다.
명령은 Skilly 저장소에서 빌드한 CLI로 실행한다. 경로는 심볼릭 링크가 없는 정규화된
절대 경로를 사용한다. macOS에서는 `/tmp` 대신 `/private/tmp` 같은 실제 경로를 쓴다.

## 전체 DB 백업과 복원

```sh
npm run build
node dist/runtime/local/main.js backup --db /absolute/memory.sqlite --output /absolute/backups/new-backup
node dist/runtime/local/main.js restore --input /absolute/backups/new-backup --output /absolute/restored/new-copy
```

`--output`의 부모 폴더는 미리 있어야 하며 **출력 폴더 자체는 없어야 한다**.
기존 폴더를 지정하면 실패하고 아무것도 덮어쓰지 않는다. 성공 응답의 `db`가 새 DB 경로다.
백업에는 다음 파일이 들어간다.

```text
new-backup/
├── manifest.json                       완료 표시·버전·시각·크기·SHA-256
├── memory.sqlite                       전체 프로젝트·기록·영수증
└── memory.sqlite.recovery.sqlite       존재하는 경우: 복구 요청과 확인·거절 이력
```

실행 중인 WAL DB도 SQLite 백업 API의 읽기 스냅샷으로 복사한다. 원본 파일 하나만
파일 복사하는 방식이 아니다. 새 사본만 단일 파일 모드로 정리하고 원본 저널 모드는 유지한다.
복원 입력에 `-wal`, `-shm`, `-journal`이 있으면 체크섬에 포함되지 않은 내용이 섞일 수 있어
거부한다. 백업 묶음을 쓰기용 DB로 사용하거나 실행 중인 DB로 바꾸지 말고 보관한다.
해시는 손상 확인용이며 서명·암호화·작성자 인증이 아니다.

### 저장 실패 요청도 보존

복구 DB의 읽기 스냅샷을 먼저 고정하고 본 DB의 스냅샷을 나중에 고정한다.
이는 요청 보관 → 본 DB 저장 → 복구 확인 순서에서 원문과 영수증이 함께 빠지는 일을 막는다.
두 파일이 정확히 같은 시각의 하나의 트랜잭션인 것은 아니다. 각각의 시각을 manifest에 기록하며,
**복구 스냅샷 이후 도착한 미저장 요청까지 보존한다고 보장하지 않는다**.
이후 쓰기까지 모두 포함해야 한다면 작업이 끝나고 새 쓰기가 멈춘 뒤 다시 백업한다.
복구 저널의 읽기 잠금 동안 새 저장 요청이 대기하거나 저장 실패로 보고될 수 있으므로,
백업·내보내기는 가능하면 진행 중 작업이 없는 때 실행한다. 자동 재시도는 하지 않는다.

원문이 없는 확인 완료 요청은 본 DB의 같은 키·해시 영수증이 있어야 한다.
복원은 대기 요청을 실행하거나 진행 중 작업을 종료하지 않는다. 복구 상태를 먼저 조회하고
허용된 원래 요청만 기존 `memory_retry_write` 절차로 재시도한다. 원본 ID·입력·해시는 유지한다.

## 프로젝트 하나만 내보내기·가져오기

조회된 실제 프로젝트 UUID를 사용한다. 폴더 이름으로 ID를 추측하지 않는다.

```sh
node dist/runtime/local/main.js export --db /absolute/memory.sqlite --project-id PROJECT_UUID --output /absolute/exports/new-project
node dist/runtime/local/main.js import --input /absolute/exports/new-project --output /absolute/imports/new-project-db
```

내보낸 폴더는 `manifest.json`과 `data.ndjson`으로 구성된다. 단순히 전체 DB를 복사한 뒤
다른 프로젝트를 삭제하는 방식이 아니다. 다음 데이터만 논리적으로 선별한다.

- 선택 프로젝트의 전체 저장소·환경에 속하는 작업·원문·정정 이력·작성 주체
- 구성요소·기능·작업 연결·구조화 보고
- 해당 프로젝트의 영수증과 전역 등록 영수증 중 소유 프로젝트가 일치하는 항목
- 해당 프로젝트의 복구 요청 원문·확인·거절 이력

다른 프로젝트 행, SQL·트리거·검색 색인 파일은 포함하지 않는다. 검색 색인은 새 DB의 자체
스키마로 다시 만든다. UUID, 프로젝트 키, 시각, revision, 당시/소급 구분과 영수증은 유지하고,
DB 내부 검색 순번(seq)은 순서를 유지해 새로 배정한다. 예전 페이지 커서는 재사용하지 않는다.
보고는 가져온 뒤에도 미검증 데이터이며 최신의 검증된 사실로 승격하지 않는다.

기록 본문이 다른 프로젝트나 비밀을 언급하는지 자동으로 판단하거나 지우지는 않는다.
인증 설정·Git 소스·별도 첨부 파일은 가져오지 않는다. 스킬 전문·보조 텍스트·모든 버전·설치 지정·파일 관측 이력은 v5 묶음에 포함한다.
설치 경로와 파일 관측은 과거 정보로 유지하며 대상 컴퓨터의 현재 설치 증명으로 삼지 않는다.
별도 첨부·바이너리 테이블은 아직 없다.

### 다른 프로젝트가 있는 DB와 합치기

```sh
node dist/runtime/local/main.js import --input /absolute/exports/new-project --db /absolute/existing.sqlite --output /absolute/imports/new-combined-db
```

기존 DB를 먼저 새 출력 폴더에 복사하고 **그 사본에만** 가져온 프로젝트를 추가한다.
기존 DB의 다른 프로젝트·대기 요청은 보존된다. 원본은 그대로 사용 중일 수 있으며 사본 생성
이후의 변경은 자동 동기화되지 않는다. 이 명령은 정본 전환·자동 연결 변경·독립 이전 완료가 아니다.
새 경로 연결은 결과를 확인한 뒤 별도로 결정한다.

프로젝트 ID·키, 작업/기록 ID, 전역 등록을 포함한 영수증 키가 겹치면 자동 덮어쓰기·병합하지
않고 실패한다. 같은 출력 경로 재실행도 거부하므로 중복 삽입하지 않는다. 이 버전에는 자동
재개/충돌 병합이 없다. 새 출력 경로로 재시도할 수 있지만 성공한 사본을 또 합치면 충돌한다.

## 실패와 지원 범위

- 본 DB v4–v5, 복구 DB v1의 알려진 스키마만 지원한다. 알 수 없는 SQL 객체나 버전은 거부한다.
  이전 버전의 원본을 이 명령이 자동 마이그레이션하지 않는다.
- 프로젝트 묶음은 최대 64 MiB, 100,000행, 한 행 256 KiB다. 메모리는 한 줄씩 읽도록 제한한다.
  전체 SQLite 백업에는 이 프로젝트 묶음 상한을 적용하지 않는다.
- 출력 폴더는 `0700`, 파일은 `0600`이다. 원문과 복구 요청을 포함하므로 개인 로컬 폴더에서 보관한다.
  같은 OS 사용자 권한의 악성 프로세스까지 막는 별도 샌드박스는 아니다.
- 백업/내보내기는 마지막 `manifest.json`, 가져오기는 마지막 `import.json`이 있어야 완료다.
  오류·중단 때 새 폴더가 남을 수 있다. **완료 표시가 없는 결과는 사용하지 않는다**.
  명령은 불완전한 출력도 삭제하지 않는다. 오류 응답은 저장·복원 성공을 뜻하지 않는다.
- 어떤 명령도 원본 기록 삭제, 외부 전송, 자동 재시도, 원본 쓰기 차단·정본 전환을 하지 않는다.
  클라우드 D1 왕복, 팀 권한과 인증, 파일 정리·암호화는 별도 후속 범위다.

## 검사

`npm run build && node --test tests/transfer.test.mjs`는 합성 임시 DB만 사용한다.
전체/프로젝트 왕복, 다중 프로젝트 격리, WAL 스냅샷, 영수증·복구 요청·소급 구분·검색 보존,
합치기 충돌, 손상 입력·과대한 행·지원하지 않는 버전·WAL 덧씌우기 거부를 확인한다.
이 검사는 실제 사용자 DB의 백업 성공이나 AI 기록 내용의 정확성을 증명하지 않는다.
