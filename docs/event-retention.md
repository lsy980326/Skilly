# 훅 이벤트 보관과 용량

훅 이벤트는 작업일지와 별개인 최소 수신 메타데이터다. 이벤트가 저장돼도
작업 원문 저장이나 내용 검증을 뜻하지 않는다. 받지 못한 이벤트의 수·내용은
알 수 없으며 복구 대기나 누락 0건으로 표시하지 않는다.

## 기본 정책과 선택적 구간 보관

기존 companion v1/v2는 전체 10,000건 한도를 그대로 유지한다. 훅 실행,
연결, 설치, 빌드, 읽기만으로 새 보관 정책을 활성화하지 않는다.

명시적으로 활성화한 companion v3는 기존 `events`, `task_links`,
`event_task_links.saved_json`을 수정·삭제·재번호화하지 않는다. 같은 SQLite에
append-only 구간 경계와 활성화 기준점만 추가한다. 현재 구간이 10,000건이면
다음 이벤트를 저장하는 동일 트랜잭션에서 다음 구간을 연다. 이전 구간은 조회와
전체 백업에 계속 포함된다. 파일을 분리하거나 디스크 공간을 비우는 기능은 아니다.

- 최대 8구간. 활성화 전의 이력이 있으면 그 이력도 한 구간을 사용한다.
- 구간당 최대 10,000 이벤트. 전체 연결 행은 최대 80,000개.
- DB 본체 최대 64 MiB. SQLite journal 등 일시 파일은 이 값에 포함되지 않는다.
  원자적 저장을 위한 32페이지 여유를 남겨두므로 실제 중단은 64 MiB 도달 전일 수 있다.
- 수신 ID 중복 확인을 한도 검사보다 먼저 수행한다. 같은 ID의 재시도는 새 구간이나
  이벤트를 만들지 않는다. 구간 추가와 이벤트 저장 실패는 함께 롤백된다.
- 전체 구간·본체·연결 한도를 넘으면 새 쓰기를 거부하고 원래 데이터를 보존한다.
  자동 삭제·외부 보관·실패 이벤트 대기열·미수신 이벤트 재구성은 하지 않는다.

## 활성화와 연결 기준

명시한 DB의 상태를 먼저 확인하고 반환된 `expect`를 사용한다.
명령은 기존 이벤트 파일이 있어야 하며 다른 DB를 만들거나 client 설정을 바꾸지 않는다.

```sh
skilly events-retention-status --db /absolute/test/memory.sqlite
skilly events-retention-enable --db /absolute/test/memory.sqlite --expect <preview-hash>
```

미리보기 이후 저장소의 상태·파일 식별이 바뀌면 다시 검토해야 한다.
활성화 전 이벤트·연결의 행은 그대로 남는다. 다만 수집 중단 동안 놓친 세션 경계를
추정하지 않도록 기존 링크는 새 이벤트에 자동 적용하지 않는다. 새 관측 ID로
자기 active 작업에 명시적으로 연결한 이후만 capture한다. 이전 active 작업에 대한
충돌 검사는 유지하며 다른 세션의 작업을 닫거나 인수하지 않는다.
정상적인 보관 구간 전환은 세션 경계가 아니므로 활성화 이후의 건강한 연결은 이어진다.

`capture_epoch_binding`은 활성화 기준 이후의 명시 연결 **이력**이다.
현재 호스트 세션·실행 중·완료 여부나 모든 이벤트 수신을 보증하지 않는다.

## 상태 확인과 호환 경계

MCP `memory_recovery_status.lifecycle_observations.event_retention`과
`memory_get_status.task_recording.event_retention`, 화면의 작업 정보 →
어디까지 저장됐나요 → 훅 이벤트 보관 상태에서 같은 정책을 확인한다.
화면의 ‘저장 문제’ 목록 위에서도 보관 상태를 확인할 수 있다.
수치는 선택한 프로젝트만의 수가 아니라 공유 event companion 전체 수다.

`ready`는 정책상 수신 시도가 가능, `rollover_ready`는 다음 수신 때 새 구간 생성,
`activation_required`는 기존 1만 건 한도로 수집 중단,
`retention_full`·`storage_full`은 새 정책의 보관 예산으로 수집 중단을 뜻한다.
접근 권한·디스크 여유·훅 신뢰·호스트 로딩 성공을 보증하지 않는다.

v3 전체 백업·복원은 구간·활성화 기준·원래 이벤트·연결·중단 저장 JSON을 보존하고
schema·구간·관계·영수증을 검증한다. 기존 v1/v2 프로젝트 교환 계약은 유지한다.
**v3 프로젝트별 export/base merge/cutover/SQLite↔D1 이동은 아직 지원하지 않는다.**
해당 경로는 출력이나 쓰기 권한 전환 전에 거부한다. 이전 작업 중인 managed 저장소도
활성화를 거부해 기존 실패 복귀 경로를 깨지 않는다. 따라서 프로젝트 독립 이전이
필요한 실사용 저장소는 이 호환 경계가 보완되기 전 활성화하지 않는다.

활성화와 이전 시작은 main DB의 쓰기 잠금을 공통 경계로 사용하고 실제 fence 직전에
정책을 다시 확인한다. 동시 상태 변경으로 이미 준비 폴더가 생긴 경우 미완성 폴더는
남을 수 있지만, 새 capability를 발견한 뒤 원본 writer를 차단하지 않는다.
