# Skilly 사용과 직접 확인

평소에는 Codex에게 개발 작업을 요청하면 된다. Skilly는 AI가 전달한 작업 내용을
로컬 DB에 보관하고 다음 작업에서 찾도록 돕는다. 사용자가 SQL을 작성하거나
매번 “기록해줘”라고 말할 필요는 없다. 다만 모델의 지침 수행에 의존하므로
누락 가능성이 있으며, 저장 성공과 설명의 정확성은 서로 다르다.

## 처음 연결 확인

이 프로젝트에는 MCP 설정과 스킬이 설치돼 있지만, 사용할 채팅에서 도구가
노출됐는지는 별도로 확인해야 한다. 설치 명령을 반복 실행하지 않는다.
다른 프로젝트를 연결할 때는 [설치 안내](codex-integration.md#프로젝트-식별과-설치)를 따른다.

1. Codex에서 Skilly 프로젝트를 열고 새 채팅을 시작한다.
2. 입력창에서 `/mcp`로 `skilly`가 연결됐는지 확인한다.
3. 없다면 설정의 MCP 서버 목록에서 활성 상태를 확인하고 지원되는 `Restart`를
   사용한 뒤 다시 확인한다. 프로젝트 신뢰 확인이 필요하면 Codex의 안내를 따른다.
4. “이 프로젝트의 Skilly 연결과 최근 작업을 확인해줘”라고 요청한다.
   연결 실패를 알리면 저장됐다고 가정하지 않는다.

새 프로세스의 연결 성공은 기존 채팅에 도구가 추가됐다는 증거가 아니다.
앱의 메뉴는 [공식 MCP 안내](https://learn.chatgpt.com/docs/extend/mcp)를 기준으로 한다.
Skilly에 로그인이나 클라우드 계정 연결을 추가할 필요는 없다.

## 평소 작업과 다음 채팅

평소에는 “댓글 오류를 수정해줘”처럼 요청한다. AI는 이전 기록 조회, 작업 시작,
중요 변경 기록, 종료 요약 저장을 수행하도록 설정되어 있다.
종료 답변의 저장 상태와 작업 ID·요약 ID를 확인하면 된다.
저장 실패나 일부 저장이라면 완료된 기록처럼 취급하지 않는다.
기록을 사용하는 일반 코드 수정은 작업 시작 저장이 성공한 후에 진행한다.
도구가 없거나 저장이 실패하면 추가 구현을 멈추고 연결 복구를 안내한다.
사용자가 “이번 작업은 기록하지 말고 진행해”라고 명시하면 기록 없이 진행한다.
읽기 전용 설명과 사용자가 요청한 연결 문제 수리는 제한을 알리고 진행할 수 있다.

다음 채팅에서는 “지난 댓글 오류 수정 작업은 어디까지 됐고 남은 일은 무엇이야?”라고
물어본다. 이전 대화를 붙여넣을 필요는 없다. 같은 프로젝트 식별 정보와 같은 DB가
연결돼 있어야 한다. 필요하면 “사용한 기록 ID도 보여줘”라고 요청해 앞선 ID와 비교한다.

로컬 MCP·DB 사용은 외부 업로드와 다르다. “클라우드 업로드 금지” 상태에서도
허용된 로컬 기록은 사용할 수 있다. 기록하지 않으려면 “이번 작업은 기록하지 마”라고
명시한다. 이 선택이나 MCP·DB 쓰기 금지는 스킬보다 우선한다.

## 터미널에서 저장 내용을 직접 보기

Skilly 폴더에서 다음을 실행한다. 최초 설치 또는 소스 변경 후에는 `npm run build`를
먼저 실행한다. 조회 명령 자체는 기존 DB를 읽기 전용으로 열며, 새 DB 생성·프로젝트
등록·기록 저장·모델 호출·네트워크 연결을 하지 않는다.

```sh
npm run memory:inspect -- \
  --project /Users/yeop/project/Skilly \
  --db /Users/yeop/project/Skilly/.skilly/memory.sqlite
```

최근 작업 5건의 ID·목표·상태와 각 작업의 최근 기록 5건을 보여준다.
본문은 최대 240자로 줄여 보여주며 전체 대화 로그를 출력하지 않는다.
작업이 많으면 `--limit 10`, 특정 작업만 보려면 `--run 작업_UUID`,
JSON 결과가 필요하면 `--json`을 추가한다. 다른 프로젝트에서는 경로를 맞춘다.
미완료·중단 작업과 복구 보관 요청은 `--attention`으로 확인한다.
복구 절차와 당시/소급 보고의 차이는 [중단·저장 실패 복구](recovery.md)를 따른다.

확인할 것은 작업 ID, 변경 기록(`change` 등), 종료 요약(`summary`)의 존재다.
변경이 없는 질문·검토 작업에는 변경 기록이 없을 수 있다.
현재 작업이 화면에 보이지 않으면 작업 ID나 같은 DB·프로젝트 범위인지 먼저 확인한다.
`summary`라는 종류만으로 종료를 단정하지 않고 작업 상태도 함께 본다.

`active`는 작업을 시작했지만 아직 종료 처리가 저장되지 않은 상태로, 진행 중이거나
종료 기록이 누락됐을 수 있으므로 실패를 뜻하지 않는다.
`completed`는 종료 요약과 함께 작업을 마감한 상태이며, 기록 내용의 정확성이나
검증 성공을 보장하지 않는다.
`interrupted`는 작업을 중단했다고 종료 요약과 함께 기록한 상태이며, 중단 이유나
내용의 정확성은 상태만으로 알 수 없다.

이 명령은 **저장된 기록의 존재**만 확인한다. Codex의 현재 연결, 기록 누락 여부,
내용의 정확성을 자동 판정하지 않는다. 미검증 상태는 오류 표시가 아니다.

## 테스트와 연결 점검은 다르다

`npm test`는 임시 DB로 코드·도구 계약을 검사한다. 실제 작업 AI의 자동 기록 성공을
증명하지 않는다. 실제 저장 흐름은 일반 작업 요청 뒤 위 조회 명령으로 확인하고,
새 채팅에서 같은 기록을 다시 찾는지 대조한다.

다음 점검은 설치된 설정으로 새 Codex 프로세스의 연결만 확인한다. macOS용이며,
모델 실행과 작업 기록 작성은 하지 않는다. MCP 시작 과정에서 설정된 DB를 열거나
초기화할 수 있으므로 순수 DB 읽기 확인은 위 `memory:inspect`를 사용한다.

```sh
node scripts/verify-codex.mjs --configured \
  --project /Users/yeop/project/Skilly \
  --db /Users/yeop/project/Skilly/.skilly/memory.sqlite \
  --codex /Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex
```

`sessions` 두 항목의 `mcp_connected: true`를 확인한다. 기본 기록 도구는 7개이며,
복구 기능을 포함한 새 서버는 9개와 `recovery_tools_available: true`를 반환한다.
`connection_check_passed: true`는 두 새 프로세스의 연결 검사 성공이며,
현재 채팅이 복구됐다는 뜻은 아니다. `host_hooks_and_plugins_preserved: true`로
기존 훅·플러그인을 유지한 검사임을 표시한다.
`mcp_dependency_declared: true`는 스킬이 MCP 의존성을 선언했다는 뜻이다.
`implicit_skill_execution_verified: false`는 이 연결 검사에서 모델을 실행하지 않아
자동 수행을 확인하지 않았다는 뜻이다. 설치된 Codex 실행 파일의 위치가 다르면
`--codex` 경로를 바꾼다.

진단은 원시 설정을 요청하지 않는다. 따라서 `effective_mcp_config_matches`는
`null`이고 설치된 서버의 실제 DB 경로 일치도 이 검사로 확인하지 않는다.
기존 서버와 훅은 시작 과정에서 실행될 수 있으므로 부작용 없는 조회라고 보지 않는다.

구현 중지 규칙은 스킬·프로젝트 지침이며 강제 실행 수집기가 아니다.
현재 채팅에서 실제 도구 호출과 저장 응답을 확인해야 연결 복구로 인정한다.
