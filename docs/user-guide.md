# Skilly 사용과 직접 확인

평소에는 Codex에게 개발 작업을 요청하면 된다. Skilly는 AI가 전달한 작업 내용을
로컬 DB에 보관하고 다음 작업에서 찾도록 돕는다. 사용자가 SQL을 작성하거나
매번 “기록해줘”라고 말할 필요는 없다. 다만 모델의 지침 수행에 의존하므로
누락 가능성이 있으며, 저장 성공과 설명의 정확성은 서로 다르다.

## 작업일지는 DB에, 안내 문서는 파일에

일반 작업의 계획·진행 상황·변경 내용·테스트 결과·인수인계·소급 보고는
Skilly DB에만 저장한다. 매 작업마다 MD 작업일지를 만들거나 기존 일지에
덧붙이지 않는다. README에 날짜별 일지를 붙이거나 다른 확장자로 우회하지도 않는다.
작업 계약과 사용자에게 보여주는 결과 설명은 채팅에 남긴다.

README·AGENTS·SKILL·API·설계처럼 계속 관리하는 고정 안내 문서는 필요한 경우
수정할 수 있다. “설계서를 MD로 작성해줘”처럼 사용자가 문서를 직접 요청한 경우도
허용한다. 이때도 별도 작업일지를 추가로 만들지는 않는다.
기존 문서와 작업일지는 보존하며, 자동 삭제나 DB 이전은 하지 않는다.

저장 실패 때는 채팅에 누락 상태를 알리고 기존 중지·복구 절차를 따른다.
MD 임시 일지로 대신 저장하지 않는다. “기록하지 마”라는 요청도 파일 기록으로
우회하지 않는다. 이 규칙은 AI가 따르는 연동 지침이며 파일 생성을 차단하는
운영체제 수준의 장치는 아니다.

## 처음 연결 확인

이 프로젝트에는 MCP 설정과 스킬이 설치돼 있지만, 사용할 채팅에서 도구가
노출됐는지는 별도로 확인해야 한다. 설치 명령을 반복 실행하지 않는다.
다른 프로젝트를 연결할 때는 [설치 안내](codex-integration.md#프로젝트-식별과-설치)를 따른다.

1. Codex에서 Skilly 프로젝트를 열고 새 채팅을 시작한다.
2. 입력창에서 `/mcp`로 `skilly`가 연결됐는지 확인한다.
3. 없다면 설정의 MCP 서버 목록에서 활성 상태를 확인하고 지원되는 `Restart`를
   사용한 뒤 다시 확인한다. 프로젝트 신뢰 확인이 필요하면 Codex의 안내를 따른다.
4. “이 프로젝트의 Skilly 연결과 최근 작업을 확인해줘”라고 요청한다.
   연결 실패를 알리면 저장됐다고 가정하지 않는다.

새 프로세스의 연결 성공은 기존 채팅에 도구가 추가됐다는 증거가 아니다.
앱의 메뉴는 [공식 MCP 안내](https://learn.chatgpt.com/docs/extend/mcp)를 기준으로 한다.
Skilly에 로그인이나 클라우드 계정 연결을 추가할 필요는 없다.

## 평소 작업과 다음 채팅

평소에는 “댓글 오류를 수정해줘”처럼 요청한다. AI는 이전 기록 조회, 작업 시작,
중요 변경 기록, 종료 요약 저장을 수행하도록 설정되어 있다.
종료 답변의 저장 상태와 작업 ID·요약 ID를 확인하면 된다.
저장 실패나 일부 저장이라면 완료된 기록처럼 취급하지 않는다.
기록을 사용하는 일반 코드 수정은 작업 시작 저장이 성공한 후에 진행한다.
도구가 없거나 저장이 실패하면 추가 구현을 멈추고 연결 복구를 안내한다.
사용자가 “이번 작업은 기록하지 말고 진행해”라고 명시하면 기록 없이 진행한다.
읽기 전용 설명과 사용자가 요청한 연결 문제 수리는 제한을 알리고 진행할 수 있다.

다음 채팅에서는 “지난 댓글 오류 수정 작업은 어디까지 됐고 남은 일은 무엇이야?”라고
물어본다. 이전 대화를 붙여넣을 필요는 없다. 같은 프로젝트 식별 정보와 같은 DB가
연결돼 있어야 한다. 필요하면 “사용한 기록 ID도 보여줘”라고 요청해 앞선 ID와 비교한다.

로컬 MCP·DB 사용은 외부 업로드와 다르다. “클라우드 업로드 금지” 상태에서도
허용된 로컬 기록은 사용할 수 있다. 기록하지 않으려면 “이번 작업은 기록하지 마”라고
명시한다. 이 선택이나 MCP·DB 쓰기 금지는 스킬보다 우선한다.

## 로컬 화면으로 보기

Skilly 폴더에서 실행한 다음 터미널에 표시된 **전체 연결 주소**를 연다.

```sh
npm run view -- --db /Users/yeop/project/Skilly/.skilly/memory.sqlite
```

왼쪽에서 프로젝트, 가운데에서 작업을 고르면 오른쪽에 상세 기록이 나온다.
목표·저장소 이름으로 검색하거나 미완료·완료·중단 상태로 좁힐 수 있다.
`저장 문제` 탭에서는 보관된 실패 요청과 저장 영수증 확인 결과를 볼 수 있다.
복구 보관함이 없거나 읽기 실패인 경우에는 “문제 없음”으로 처리하지 않는다.
서버에 도착하지 못한 요청은 이 목록에도 없을 수 있다.

| 표시 | 뜻 |
|---|---|
| 최근 활동 | 미완료 작업에 5분 이내 저장된 기록이 있음. AI의 실시간 실행을 확인한 것은 아님 |
| 갱신 확인 필요 | 아직 마감되지 않았고 최근 기록이 없음. 중단 여부는 원래 AI 채팅에서 확인 |
| 완료 / 중단 | 저장된 종료 상태. 기록 내용의 정확성이나 테스트 성공과 별개 |
| 작성 주체 | AI가 작업 시작 때 제공한 이름. 사람의 로그인·신원 인증 정보가 아님 |
| 작성자 미수집 | 과거 기록 또는 작성 주체를 제공하지 않은 연결. 경로나 프로젝트 이름으로 추측하지 않음 |
| 당시 기록 / 소급 기록 | 작성 AI가 선언한 분류. 미지정 과거 기록은 그대로 “작성 시점 미지정” 표시 |
| 미검증 | AI의 보고를 보관했다는 뜻이며 자동 실행 수집·내용 검증을 하지 않음 |

새 `memory_begin_task`는 선택적으로 `actor`를 받으며 갱신된 `use-skilly`가
Codex·Cursor 같은 알려진 작성 주체를 전달하도록 안내한다.
기존에 열린 MCP 연결의 도구 목록에는 이 필드가 없을 수 있다.
새 서버에 연결된 이후 시작하는 작업부터 수집하며 과거 작업에는 소급 채우지 않는다.

화면은 이 컴퓨터의 `127.0.0.1`에서만 열린다. 일반 조회는 **읽기 전용**이며,
명시적으로 선택한 문서 가져오기만 별도 저장 경로를 사용한다.
기존 기록 편집·삭제·외부 업로드를 하지 않는다. 처음에는 전체 연결 주소의 토큰으로
인증하고 주소창에서 토큰을 지운다. 서버 조회가 성공한 연결만 같은 브라우저의
해당 출처(프로토콜·호스트·포트)별 저장소에 보관한다. 이후 새로고침·탭 재접속·
Codex 재실행에서도 같은 화면 주소로 연결을 복원하며, 모든 조회는 서버가 다시 인증한다.

브라우저 연결 정보의 보관 한도는 7일이다. 이는 서버 토큰의 유효기간과 다르다.
서버 재시작·포트 변경·브라우저 데이터 삭제·보관 만료 때는 새 전체 연결 주소가 필요하다.
비공개 탐색이나 저장 차단 환경에서는 연결 유지가 제한될 수 있으며 화면에 안내한다.
인증 거부(401)는 해당 저장 연결만 해제하고 네트워크·서버의 일시 오류는 연결을 보존한다.
화면 서버는 계속 실행 중이어야 하며, Codex를 켜는 것이 서버를 자동 실행하지는 않는다.
종료는 터미널에서 `Ctrl+C`다.

화면이 보이는 동안 15초마다 조회하며 숨겨진 탭에서는 중지한다.
“더 보기”로 이전 목록·기록을 펼치면 읽는 위치를 지키기 위해 자동 갱신을 멈춘다.
화면의 `새로고침`을 누르면 최신 첫 페이지와 자동 갱신으로 돌아온다.
페이지당 40건만 읽으며 별도 AI·프론트엔드 프레임워크·폴더 감시를 실행하지 않는다.
조회 프로그램은 실행해 둔 동안만 동작한다.

조회기는 기존 DB 스키마 v1–v5을 마이그레이션 없이 읽는다.
새 기록 서버는 DB를 v4로 갱신해 작성 주체·구성요소·기능·요약 테이블을 추가한다.
기존 작업 테이블의 열은 유지하지만 구버전 서버를 새로 시작하면 최신 스키마를 거부하므로,
한 DB를 공유하는 MCP 실행 파일은 같은 최신 버전으로 사용한다.
일반적인 DB 백업 절차는 그대로 유지한다.

## 로컬 화면 서버 관리

Skilly 저장소에서 다음 명령을 사용한다. 기본 DB는 이 저장소의
`.skilly/memory.sqlite`, 기본 포트는 `50916`이다. 다른 DB는 각 명령 뒤에
`--db /absolute/memory.sqlite`, 처음 실행할 다른 포트는 `--port 50917`을 붙인다.
처음 실행하거나 서버 소스를 업데이트한 뒤에는 `npm run build`를 한 번 실행한다.
관리 명령 자체는 매번 컴파일하지 않는다.

```sh
npm run viewer -- start
npm run viewer -- status
npm run viewer -- restart
npm run viewer -- restart-code
npm run viewer -- stop
```

- `start`: 채팅·터미널과 분리된 로컬 화면 서버를 실행한다. 이미 관리 중이면
  중복 실행하지 않고 기존 연결 주소를 반환한다. 출력된 전체 주소를 한 번 연다.
- `status`: 관리 서버의 응답과 DB 조회를 확인한다. 인증 토큰은 출력하지 않는다.
  `running`은 관리 서버 응답과 DB 조회 성공, `degraded`는 서버 응답은 있지만 DB
  경로·조회 문제, `unresponsive`는 관리 통로의 응답 실패, `stopped`는 관리 통로 없음이다.
  관리하지 않는 기존 서버까지 검색한 결과는 아니며, 실행 중인 개발 AI의 상태와도 무관하다.
- `restart`: 같은 프로세스에서 화면 파일과 읽기 전용 DB를 다시 연다(`reload_in_place`).
  주소·포트·인증은 유지한다. 새 자산과 DB 조회가 모두 준비돼야 교체하며 실패 시 기존
  화면을 유지한다. 실행 중인 TypeScript 서버 모듈 자체를 다시 로드하는 것은 아니다.
  서버 모듈을 업데이트했다면 `restart-code`를 사용한다.
- `restart-code`: 실행 중인 정상 관리 서버의 주소·인증을 메모리로 전달해 서버
  프로세스를 교체한다. 새 코드·화면·DB 조회를 먼저 확인하며 준비 실패 시 기존 서버를
  유지한다. 교체 중에는 잠시 연결이 끊길 수 있다. 종료 후 새 프로세스 시작이 실패하면
  `status`로 확인한다. 인증을 파일·명령행에 저장하거나 자동 시작을 등록하지 않는다.
- `stop`: 이 DB의 관리 서버가 맞는지 확인한 뒤 그 서버만 종료한다. DB·복구 요청·기록을
  삭제하지 않는다. 이후 `start`는 새 인증 주소를 발급한다.

인증값은 서버 메모리에만 두고 관리 파일·명령행·상태 출력에 저장하지 않는다.
정상 `restart`와 브라우저 새로고침은 같은 인증을 쓰지만 프로세스 강제 종료·PC 재부팅
후 새 `start`에서는 출력된 전체 주소로 다시 연결해야 한다. 자동 시작·재실행 감시기나
OS 서비스는 등록하지 않는다. 별도 모델·폴더 감시기도 추가하지 않는다.

관리 통로는 사용자 전용 `0700` 임시 폴더의 `0600` Unix 소켓을 사용한다.
같은 OS 사용자 권한을 가진 악성 프로세스까지 격리하는 장치는 아니다.
macOS·Linux에서 지원하며 Windows는 기존 `npm run view -- --db ...`를 사용한다.
상태 조회는 프로세스에 신호를 보내지 않는다. 시작 시에만 잠금을 잡고 응답 없는
동일 소유자의 오래된 소켓을 정리한다. 시작 도중 부모 명령이 비정상 종료해 잠금이
남으면 임의로 제거하지 않고 오류를 알린다. 관리되지 않는 기존 서버가 포트를 쓰면
그 프로세스를 종료하지 않고 시작이 실패한다. 포트 변경이나 확인된 기존 화면 서버의
종료는 별도로 결정한다. DB 폴더 자체가 사라진 경우에는 경로를 복구한 뒤 관리한다.

기존 `npm run view -- --db /absolute/memory.sqlite`는 계속 전경 실행으로 제공한다.
이 방식의 서버는 위 관리 통로에 등록되지 않는다. `file://…/ui/index.html` 대신
실행 결과에 표시된 `http://127.0.0.1:포트/` 주소를 사용한다.

## 구성요소·기능으로 살펴보기

**기능** 탭에서 항목을 선택하면 오른쪽에 기능 설명, 마지막 상태 보고,
연결 작업의 최근 변경, 남은 작업과 검사 보고를 볼 수 있다. **연결 작업 보기**는
그 기능의 작업 목록을, **최근 보고 원문 보기**는 해당 작업의 원래 타임라인을 연다.
기록 ID·저장소·환경·보고 시각을 함께 표시하므로 다른 환경의 보고와 구분한다.

기능 상태는 AI가 명시한 선언이고, 최근 작업 보고는 그 기능과 연결된 작업의
요약이다. 두 보고의 시각은 다를 수 있으며, 여러 기능에 연결된 작업은 공통 보고를
보여준다. 당시 작성된 비정정 보고만 현재 요약의 후보로 사용한다. 소급 보고·정정된
원문은 작업 타임라인에 보존하며 현재 상태를 임의로 덮어쓰지 않는다.

**실제로 확인된 실행 근거**와 **AI가 보고한 검사 결과**를 분리한다. 현재 실행
수집기가 없으므로 전자는 **미수집**이다. AI가 검사를 통과했다고 보고하거나
DB 저장 영수증이 있어도 검증된 실행 근거로 승격하지 않는다. 설명·요약·남은 작업이
없으면 미수집으로 표시하며, 미완료 작업 0개나 남은 작업 보고 없음이 기능 완료를
뜻하지 않는다. 새 요약을 생성하는 모델 호출이나 과거 기록 수정은 수행하지 않는다.

큰 화면에서는 서비스 목록 오른쪽 구분선을 잡아 목록 폭을, 상단 작업 흐름 아래
구분선을 잡아 대시보드 높이를 조절할 수 있다. 구분선에 Tab으로 이동한 뒤
방향키로 16픽셀씩, Shift와 함께 누르면 48픽셀씩 조절한다. Home/End는
최소/최대 크기다. 드래그 중 Escape를 누르면 취소한다.

크기는 이 브라우저에만 저장되며 인증 정보나 DB 기록과는 무관하다.
구분선을 두 번 클릭하면 해당 크기를, 상단 **배치 초기화**는 두 크기를 기본값으로
돌린다. 좁은 화면에서는 구분선을 숨긴다. 높이 조절은 작업 흐름을 펼쳤을 때만 가능하다.
대시보드는 처음 표시되거나 저장 내용이 바뀌면 짧게 움직인다. 미완료 작업이 있는
구성요소와 작업 카드에는 파란 테두리 빛이 반복된다. 이는 종료 기록이 없는 작업을
찾기 위한 표시이며 실제 실행 중이라는 뜻은 아니다. 운영체제의 동작 줄이기
설정에서는 반복 움직임 없이 테두리 강조만 남는다.

대시보드를 낮추면 작업 제목과 개수를 중심으로 표시한다. 높이를 늘리면 작성자와
마지막 기록 시각을 보여주며, 480픽셀 이상에서는 글과 카드도 커진다. 이때 최근
요약·브랜치와 구성요소별 미완료 작업을 최대 3개까지 표시한다. 요약이 없는 기록은
미작성으로 안내하며 원문을 임의로 요약하지 않는다. 이미 조회한 자료를 사용하므로
높이 조절 자체가 추가 DB 조회나 AI 호출을 만들지는 않는다.

서비스를 선택하면 구성요소별 연결 작업·미완료 수와 미분류 수가 표시된다.
상단 작업 흐름 보드는 최근 미완료 작업의 제목·작성 주체·연결 기능을 보여준다.
구성요소 버튼은 작업 목록을 좁히고 작업 카드는 원래 상세 기록을 연다.
이 보드는 저장된 기록 기준이며 실제 서버 가동이나 AI 실행을 감지하지 않는다.
일부 작업만 불러온 경우 실제 표시 수를 안내하며, 나머지는 목록에서 확인한다.
Web·API·Bot 버튼 또는 구성요소/기능 선택으로 작업을 좁힌다. `기능` 탭에서는
설명, 연결 작업, 최근 당시 보고를 확인하고 `연결 작업 보기`로 내려간다.
기능 상태·검사 결과는 AI의 보고이며 기능 구현과 배포를 자동 확인한 값이 아니다.

새 작업의 짧은 제목과 구조화 보고는 핵심 변화·확인 결과·제약·다음 작업으로
보인다. 원문과 출처 ID는 펼쳐 볼 수 있다. 이전 기록은 원문 미리보기와
`구조화 요약 없음`으로 표시하며 임의로 재작성하거나 서버 이름을 채우지 않는다.
타임라인은 최근 저장 순으로 연결되고 원문은 펼쳐 볼 수 있다. 새 보고가 들어올 때만
짧은 전환 효과를 사용하며 이전 기록 추가 조회에는 적용하지 않는다. 시스템의
동작 줄이기 설정에서는 애니메이션을 끈다.

AI는 `memory_query_overview`로 같은 구성요소·기능·작업을 구조화해 읽는다.
한 요청은 최대 40개 항목/32 KiB이며 `next_offset`이 있으면 다음 페이지를 읽는다.
기본은 기존 저장소·환경 범위이고 `coverage: service`를 명시해야 같은 서비스의
저장소를 함께 읽는다. 기능 최근 보고는 정정되지 않은 당시 기록을 관측 시각으로
정렬하며, 나중에 저장한 소급 보고를 현재 상태로 승격하지 않는다.

연결 JSON은 기존 범위를 유지한 채 선택적 `component: {"key":"web","name":"Web"}`를
선언할 수 있다. 갱신된 MCP와 스킬이 있는 새 연결부터 구성요소를 전달한다.
기존 프로세스의 도구·설정은 자동으로 교체되지 않으며 기존 설치 스킬은 보호된다.
v4는 기존 작업·원문·영수증을 보존한다. 새 실행 파일을 사용하고, 필요 시
기존 백업에서 복원할 수 있도록 업그레이드 전 SQLite 백업을 보관한다.

## 터미널에서 저장 내용을 직접 보기

Skilly 폴더에서 다음을 실행한다. 최초 설치 또는 소스 변경 후에는 `npm run build`를
먼저 실행한다. 조회 명령 자체는 기존 DB를 읽기 전용으로 열며, 새 DB 생성·프로젝트
등록·기록 저장·모델 호출·네트워크 연결을 하지 않는다.

```sh
npm run memory:inspect -- \
  --project /Users/yeop/project/Skilly \
  --db /Users/yeop/project/Skilly/.skilly/memory.sqlite
```

최근 작업 5건의 ID·목표·상태와 각 작업의 최근 기록 5건을 보여준다.
본문은 최대 240자로 줄여 보여주며 전체 대화 로그를 출력하지 않는다.
작업이 많으면 `--limit 10`, 특정 작업만 보려면 `--run 작업_UUID`,
JSON 결과가 필요하면 `--json`을 추가한다. 다른 프로젝트에서는 경로를 맞춘다.
미완료·중단 작업과 복구 보관 요청은 `--attention`으로 확인한다.
복구 절차와 당시/소급 보고의 차이는 [중단·저장 실패 복구](recovery.md)를 따른다.

확인할 것은 작업 ID, 변경 기록(`change` 등), 종료 요약(`summary`)의 존재다.
변경이 없는 질문·검토 작업에는 변경 기록이 없을 수 있다.
현재 작업이 화면에 보이지 않으면 작업 ID나 같은 DB·프로젝트 범위인지 먼저 확인한다.
`summary`라는 종류만으로 종료를 단정하지 않고 작업 상태도 함께 본다.

`active`는 작업을 시작했지만 아직 종료 처리가 저장되지 않은 상태로, 진행 중이거나
종료 기록이 누락됐을 수 있으므로 실패를 뜻하지 않는다.
`completed`는 종료 요약과 함께 작업을 마감한 상태이며, 기록 내용의 정확성이나
검증 성공을 보장하지 않는다.
`interrupted`는 작업을 중단했다고 종료 요약과 함께 기록한 상태이며, 중단 이유나
내용의 정확성은 상태만으로 알 수 없다.

이 명령은 **저장된 기록의 존재**만 확인한다. Codex의 현재 연결, 기록 누락 여부,
내용의 정확성을 자동 판정하지 않는다. 미검증 상태는 오류 표시가 아니다.

## 테스트와 연결 점검은 다르다

`npm test`는 임시 DB로 코드·도구 계약을 검사한다. 실제 작업 AI의 자동 기록 성공을
증명하지 않는다. 실제 저장 흐름은 일반 작업 요청 뒤 위 조회 명령으로 확인하고,
새 채팅에서 같은 기록을 다시 찾는지 대조한다.

다음 점검은 설치된 설정으로 새 Codex 프로세스의 연결만 확인한다. macOS용이며,
모델 실행과 작업 기록 작성은 하지 않는다. MCP 시작 과정에서 설정된 DB를 열거나
초기화할 수 있으므로 순수 DB 읽기 확인은 위 `memory:inspect`를 사용한다.

```sh
node scripts/verify-codex.mjs --configured \
  --project /Users/yeop/project/Skilly \
  --db /Users/yeop/project/Skilly/.skilly/memory.sqlite \
  --codex /Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex
```

`sessions` 두 항목의 `mcp_connected: true`를 확인한다. 서비스 현황 조회를 포함한 기본 도구는 8개이며,
복구 기능을 포함한 새 서버는 10개와 `recovery_tools_available: true`를 반환한다.
`connection_check_passed: true`는 두 새 프로세스의 연결 검사 성공이며,
현재 채팅이 복구됐다는 뜻은 아니다. `host_hooks_and_plugins_preserved: true`로
기존 훅·플러그인을 유지한 검사임을 표시한다.
`mcp_dependency_declared: true`는 스킬이 MCP 의존성을 선언했다는 뜻이다.
`implicit_skill_execution_verified: false`는 이 연결 검사에서 모델을 실행하지 않아
자동 수행을 확인하지 않았다는 뜻이다. 설치된 Codex 실행 파일의 위치가 다르면
`--codex` 경로를 바꾼다.

진단은 원시 설정을 요청하지 않는다. 따라서 `effective_mcp_config_matches`는
`null`이고 설치된 서버의 실제 DB 경로 일치도 이 검사로 확인하지 않는다.
기존 서버와 훅은 시작 과정에서 실행될 수 있으므로 부작용 없는 조회라고 보지 않는다.

구현 중지 규칙은 스킬·프로젝트 지침이며 강제 실행 수집기가 아니다.
현재 채팅에서 실제 도구 호출과 저장 응답을 확인해야 연결 복구로 인정한다.

## 스킬 보기

프로젝트의 **스킬** 탭에서 버전·전문·설치 안내와 마지막 파일 관측을 본다.
등록·지정·명시적 점검 방법과 상태의 의미는 [스킬 라이브러리](skill-library.md)를 따른다.
파일 일치는 AI가 스킬을 로딩하거나 실행했다는 뜻이 아니다.

## 동시 작업과 리소스 측정

실제 명령 결과를 AI 보고와 구분해서 보려면 [로컬 실행 결과 수집](execution-results.md)을 따른다.
명시적으로 실행기를 거친 프로세스만 대상이며 훅 자동 설치·전체 명령 관측은 포함하지 않는다.

macOS/Linux에서 다음 명령을 실행한다. 기본 시험은 준비 시간 외에 부하 10분과
부하 전후 유휴 각 30초가 걸린다. 실사용 DB나 설정을 입력받거나 변경하지 않는다.

```sh
npm run bench:stability
# 수시간 검사는 같은 조건을 유지하며 시간을 늘린다. 예: 1시간
npm run bench:stability -- --seconds 3600
# 측정기 동작만 빠르게 확인하는 시험 (안정성 판정용 아님)
npm run bench:stability -- --seconds 3 --idle-seconds 1 --seed-records 200 --clients 2
```

기본 조건은 20개 테스트 프로젝트·합성 기록 1만 건·MCP 프로세스 4개와 별도 화면 서버다.
각 연결은 목표 주기 250ms마다 작업 시작·변경·원문 조회·검색·현황 조회·종료를 실행한다.
실제 작업은 이보다 뜸하게 기록한다. 같은 프로젝트에 대한 경합과 서로 다른 프로젝트의
작업을 번갈아 실행하고, 화면 API 3종도 500ms마다 조회한다.
요청 처리에 시간이 더 걸리면 중첩시키지 않고 실제 처리량을 보고한다.

터미널에 30초 구간별 CPU·RSS와 최종 p50/p95/최대 지연, 재시도 오류 종류를 출력한다.
CPU는 **코어 하나를 100%**로 계산하며 프로세스별로 표시한다. RSS는 5초 간격 표본이며
운영체제의 메모리 회수와 런타임 캐시 영향을 받는다. 시험 운전자와 다른 앱의 비용은
포함하지 않는다. 요청 지연에는 같은 입력·키로 재시도한 시간도 포함한다.
장비별 성능 기준값은 강제하지 않는다. `passed`는 시험·저장 대조·종료가 완료됐다는
뜻이며, 특정 CPU·메모리·응답 시간 목표를 통과했다는 뜻은 아니다.

종료 시 저장 응답을 받은 모든 기록 ID와 DB의 전체 ID를 대조하고, 무결성·외래키·미종료
작업·남은 복구 요청을 검사한다. 새 MCP 프로세스로 원문과 검색도 다시 조회한다.
Ctrl-C 또는 SIGTERM은 진행 중 요청을 정리하고 테스트 서버를 종료하며 성공으로 표시하지 않는다.
성공은 테스트 연결 종료까지 확인한 경우에만 표시한다. 강제 종료(SIGKILL)나 시스템 종료는
정리할 수 없다. 출력된 임시 폴더의 합성 DB는 재점검용으로 남긴다.

이것은 제한된 시간의 합성 시험이다. 수일간 메모리 누수 부재, 실제 Codex 채팅의 스킬
자동 호출, 브라우저 렌더링 비용이나 전달되지 않은 기록 누락까지 증명하지 않는다.
특히 MCP 연결 수만큼 Node 프로세스의 기본 메모리 비용이 늘어난다.

### 검사 근거 읽기

작업·기능 상세의 **검사 근거**는 보고의 정확성을 판정하는 표시가 아니다.

- **AI 보고만 있음:** 구조화된 검사 보고는 있지만 조회한 범위에 직접 실행 관측이 없다. 미실행을 뜻하지 않는다.
- **직접 실행 관측 있음:** 종료 결과를 수집한 프로세스가 있다. 실패 종료도 관측이며, 개별 검사와의 대응이나 기능 검증 완료를 보장하지 않는다.
- **확인 불가:** 보고·관측이 없거나, 종료 미확인·조회 정보 부재·읽지 않은 페이지 때문에 판단할 수 없다.

AI 검사 항목은 직접 실행 관측이 있어도 계속 AI 보고로 표시한다. 기능 화면의 관측 수는
연결 작업 전체, AI 검사 보고 수는 현재 표시한 최근 보고를 기준으로 하므로 서로 일대일 대응하지 않는다.

## 화면 갱신

자동 조회는 화면이 보이는 동안 15초마다 동작하며 검색창에 커서가 있어도 계속된다.
숨긴 탭에서 돌아오면 즉시 다시 읽는다. 상단 새로고침은 최신 첫 페이지부터 다시
읽으며, 기존 기록은 바꾸지 않는다. 확인 시각은 초 단위로 표시한다.
요청이 10초 넘게 끝나지 않으면 시간 초과를 표시하고 버튼을 다시 사용할 수 있다.

더 보기로 펼친 이전 기록은 자동 조회 중 유지한다. 최신 기록과 이전 페이지 사이의
조회 공백 가능성이 있으면 안내하며 상단 새로고침으로 최신부터 다시 읽을 수 있다.
연결 주소·인증 오류는 별도로 표시하며 인증을 건너뛰어 갱신하지 않는다.

기존 문서 가져오기는 [선택한 Markdown 원문 가져오기](markdown-import.md)를 따른다.

## 화면에서 문서 가져오기

서비스를 선택한 뒤 상단 **문서 가져오기**에서 저장할 작업 공간과 UTF-8 Markdown
한 개(최대 48 KiB)를 선택한다. **원문 미리보기**는 DB에 쓰지 않는다. 문서 이름은
출처를 구분하는 표기이며 브라우저는 실제 폴더 경로를 제공하지 않는다.
내용을 확인한 뒤 **소급 기록으로 가져오기**를 누르면 별도의 가져오기 작업에
원문을 저장한다. **저장된 기록 보기**에서 소급·미검증 표시와 원문을 확인한다.
원본 파일과 기존 기록은 그대로다. 같은 원문·문서 이름·저장 위치를 다시 요청해도
원문을 중복 저장하지 않는다. 저장 응답을 받지 못하면 같은 선택으로 다시 시도한다.

저장 단계의 움직이는 점과 빛은 미완료 기록의 **마감 대기**를 나타내며, 실제 AI
실행을 감지한 신호가 아니다. 종료·중단된 작업은 움직이지 않으며 시스템의
동작 줄이기 설정을 따른다.
