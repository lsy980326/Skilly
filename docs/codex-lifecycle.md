# Codex 실행 이벤트와 기록 연결

이 기능은 지원되는 Codex 훅에서 **이벤트를 받았다는 사실**을 저장하고,
작업 AI에 기존 MCP 기록 절차를 상기시킨다. 작업 내용은 여전히 MCP의
시작·변경·종료 영수증으로 확인한다. 훅은 MCP 연결을 대신 복구하지 않는다.

## 지원 확인과 적용 경계

2026-10-22 [공식 Hooks 문서](https://learn.chatgpt.com/docs/hooks)와 설치된
Codex CLI 0.144.4의 `hooks stable true`를 확인했다. 후보는 `SessionStart`,
`PostToolUse`, `PreCompact`, `Stop`, `Interrupt`, `SessionEnd`를 사용한다.
도구 후처리는 `Bash`와 `apply_patch`만 대상으로 하여 Skilly MCP 호출을
다시 기록하도록 유도하는 순환을 피한다. 모든 도구 경로를 관측하지 않는다.

`Stop`은 AI 턴 종료이며 작업 성공·종료가 아니다. `Interrupt`는 사용자 중단
관측이며 프로세스 강제 종료를 탐지하지 않는다. 세션 시작은 MCP 준비보다
빠를 수 있다. 훅 오류·미승인·미지원 호스트에서는 실행이 생략될 수 있다.

프로젝트 신뢰와 **정확한 훅 정의에 대한 사용자 신뢰**가 각각 필요하다.
후보 생성, CLI 직접 호출, 별도 MCP 연결 성공은 실제 Codex 훅 로딩 증거가 아니다.

## 설정을 보존하는 후보 생성

```sh
npm run setup:hooks -- --project /absolute/existing-project \
  --db /absolute/test-memory.sqlite --output /absolute/new-candidate
```

새 후보의 `.codex/hooks.json`만 생성한다. 기존 설정을 읽거나 덮어쓰지 않고,
신뢰도 추가하지 않는다. 검토한 정의만 호스트의 지원 절차로 병합하고 사용자가
훅을 신뢰해야 한다. 기존 훅 파일을 후보로 통째로 교체하지 않는다.
폴더를 옮긴 뒤에는 새 실제 경로로 후보를 다시 만들고 재검토한다.

기록 거부 세션에서는 훅도 꺼야 한다. 이 수집기는 프롬프트를 읽지 않으므로
자연어의 기록 거부를 스스로 감지하지 않는다. 훅 프로세스 환경의
`SKILLY_RECORDING=off` 또는 호스트의 훅 비활성화를 사용한다. 스킬만 기록을
중단했다고 해서 이미 설치된 훅까지 꺼졌다고 주장하면 안 된다.

## 저장하는 정보

본 DB를 수정하지 않고 `<db>.events.sqlite`에 저장한다. 새 파일 권한은 0600이다.
프로젝트 키·저장소·환경, 실제 프로젝트 경로 해시, 세션·턴 해시, 이벤트 종류,
시작 종류, 도구 분류, 실제 수신 시각만 보존한다. 도구 호출 ID는 중복 방지용
해시에만 사용한다. 명령·인수·출력·프롬프트·최종 답변·대화 파일은 보존하거나
열지 않는다. 전달된 `transcript_path`도 사용하지 않는다.

입력은 128 KiB, 전체 이벤트는 10,000건, 조회는 최근 20건으로 제한한다.
상한·잠금·접근 실패 시 기존 항목을 지우지 않고 실패한다. 이벤트 저장 실패를
복구 대기라고 표시하지 않는다. 수집 실패를 가리기 위한 별도 저널은 만들지 않는다.
이 메타데이터는 작업 원문이 아니며 현재 백업·프로젝트 교환 묶음에 포함되지 않는다.

## 재연결 후 확인

새 빌드로 연 프로젝트별 MCP의 `memory_recovery_status`는 기존 요청 영수증과
원래 입력 보관 상태에 더해 `lifecycle_observations`를 반환한다.

| 항목 | 의미 |
|---|---|
| 요청 `delivery_status: saved` | 본 DB의 작업 기록 영수증 존재 |
| 요청 `recovery_pending` | 원래 작업 요청이 보관됨. 동일 요청만 허용 범위에서 재시도 |
| 이벤트 `observations_available` | 훅 입력의 최소 메타데이터가 저장됨. 작업 내용 저장과 별개 |
| 이벤트 `not_observed` | 이 경로·범위에서 관측 없음. 설치 안 됨·미실행·누락을 단정하지 않음 |
| 이벤트 `unavailable` | 관측 저장소 조회 실패. 정상 빈 목록으로 취급하지 않음 |

원시 이벤트 목록은 작업 ID를 추정하지 않는다(`work_record_linkage: not_observed`).
선택적 명시 연결은 아래 절을 따른다. 같은 프로젝트의 다른 채팅을 추정하여 닫지 않는다.
입력 출처는 `local_hook_input / authenticity: not_attested`이고 모든 주장 검증은 false다.
`missing_record_count: null`, `completeness: unknown`을 유지한다.

새 연결에서는 복구 상태를 조회하고 사용자 요청에 해당하는 보관 요청만
`memory_retry_write`로 재시도한다. 훅 메타데이터에서 빠진 작업 설명을 재구성하거나,
다른 세션을 닫거나, 이미 실행한 검사를 재실행해 영수증을 만들지 않는다.

## 확인 범위

회귀 검사는 직접 훅 입력을 전달하는 계약 검사와 실제 로컬 stdio MCP 프로세스
중단·재연결 검사를 구분한다. 직접 전달한 fixture 이벤트는 Codex가 발생시킨
이벤트로 보고하지 않는다. 새 설치·이동 후보의 경로와 로컬 동작을 확인해도
실제 앱 설정 로딩·신뢰 승인·훅 실행은 해당 호스트에서 따로 확인해야 한다.

## 작업과 명시적으로 연결

새 MCP의 `memory_link_task_events`에 자신의 `project_id`, 저장된 활성 `run_id`,
**현재 훅 안내가 제공한** `observation_id`를 보낸다. 원시 목록에서 다른 채팅의
ID를 고르거나 시간·프로젝트 이름으로 연결하지 않는다. 연결은 AI의 명시적 선언이며
사용자 신원이나 세션 소유권의 암호학적 증명은 아니다.

관측 안내가 전달된 뒤 연결 도구가 도착하기 전에 다른 도구 이벤트가 추가될 수 있다.
따라서 같은 세션에서 중간 `PostToolUse`·`PreCompact`가 생겨도 명시한 관측은 사용할 수 있다.
호스트의 `turn_id`는 도구 호출 사이에도 달라질 수 있는 불투명한 값이며 사용자 턴의 경계로 추정하지 않는다.
대신 관측 뒤 같은 범위·루트·세션에 `Stop`·`Interrupt`·`SessionEnd`·`SessionStart`가 있으면
`stale_anchor`로 거절한다. 알 수 없는 이벤트도 거절하며 닫는 이벤트 자체를 연결 기준으로 쓰지 않는다.
다른 세션의 이벤트는 이 세션의 기준을 만료시키지 않는다. 목록에서 대체 관측을 자동 선택하지 않는다.
이는 저장된 경계를 확인하는 규칙이며 같은 사용자 턴의 증명은 아니다. 훅이 놓친 경계는 알 수 없다.

연결은 **연결이 저장된 뒤** 수신한 이벤트에만 적용한다. 안내 전달과 연결 저장 사이의
이벤트도 소급 연결하지 않는다. 과거 이벤트·기록·작업 상태를
바꾸지 않는다. 다른 열린 작업으로 연결 전환은 거절하고, 같은 작업의 재요청은 기존
연결 영수증을 반환한다. fork 세션은 연결을 상속하지 않는다. 종료된 작업에는 이후
이벤트를 붙이지 않는다. 폴더 이동 후에는 새 루트의 관측으로 다시 연결해야 한다.

`memory_get_status.task_recording`과 화면 상세는 같은 읽기 모듈을 사용한다.

- `last_saved`: 지금 본 DB에서 확인되는 마지막 기록 ID·순서·저장 시각과 영수증 여부.
- `interruption`: 명시적으로 연결된 중단 관측과 그 처리 중 읽은 저장 지점.
- `association_unconfirmed`: 본 DB 접근 등으로 연결을 확인하지 못한 이벤트 수.
- `linkage: not_linked | unavailable`: 연결 없음과 조회 실패를 구분.

본 DB와 이벤트 DB 사이에는 하나의 트랜잭션이 없다. 중단 시점의 스냅샷은 훅 처리 중
확인한 저장 지점이며, 동시 쓰기를 포함한 정확한 경계나 저장 누락을 증명하지 않는다.
실패한 연결을 자동 재생·소급 연결하지 않는다. 복구 대기는 기존 원래 요청 보관함에서
별도로 확인한다. 중단 이력이 있어도 작업을 자동 종료하거나 현재 실행 중이라고 단정하지 않는다.

연결과 스냅샷은 기존 이벤트 sidecar의 추가 테이블에 보존한다. 본 DB 스키마와 기존
행은 변경하지 않는다. 기존 이벤트만 있는 sidecar도 읽을 수 있다. 전체 DB 백업·복원은
v2 묶음에 이 메타데이터를 포함한다. 프로젝트별 논리 교환에는 아직 포함하지 않는다.
루트·세션 해시는 유지하며 이동한 루트는 연결을 상속하지 않으므로 새 연결이 필요하다.
자세한 범위와 복원 검사는 [백업 안내](local-transfer.md)를 따른다.
