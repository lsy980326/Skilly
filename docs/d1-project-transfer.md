# D1 프로젝트 독립 이전

## 지원 범위

`D1ProjectTransfer`는 호스트가 명시적으로 전달한 **로컬 D1 binding** 사이에서 프로젝트
하나를 이전하는 비동기 모듈이다. `008-project-transfer.sql`을 001–007 다음 신규/테스트
D1에 명시적으로 적용한다. 실사용 SQLite v15나 자동 마이그레이션에는 등록하지 않는다.
네트워크 클라이언트·원격 인증·MCP 설치·연결 설정 변경·삭제는 포함하지 않는다.

SQLite와 D1은 스킬 지정·실행 JSON·이벤트 저장 형식이 다르다. 이 묶음은
`skilly-d1-project` v1이며 기존 `skilly-local-transfer`와 직접 호환되지 않는다.
**D1 → D1 독립 이전**을 지원하며 SQLite ↔ D1 변환은 별도 어댑터가 필요하다.
다른 프로젝트가 있는 목적지에 병합하지 않고, 비어 있는 별도 업무 DB만 사용한다.
따라서 원문 순번과 중단 시점의 저장 지점 JSON을 바꾸지 않고 보존할 수 있다.

## 내보내기·가져오기

`exportD1Project(binding, projectId)`는 먼저 봉인된 프로젝트만 읽는다. 프로젝트 revision
전후를 확인하고 변경되면 최대 3회 다시 읽는다. 작업 목록의 잘린 요약 API를 이용하지
않으며 **26개 업무 테이블**의 원문·관계·영수증·순번을 명시적으로 포함한다.
다른 프로젝트, FTS 내부 자료, 운영 제어·인증·연결 설정은 포함하지 않는다.

- 작업·보고·구성요소·기능과 별칭·코드 경로
- 결정·정정·철회, 계획 버전·완료 조건·진행 보고
- 실행 결과·검사 상세·소스 관측, 계획의 실행 연결
- 수신 이벤트·작업 연결·중단 당시 저장 지점
- 스킬 전문·패키지 파일·버전·설치 지정 이력·파일 관측·AI 사용 보고
- 원래 요청 키·내용 해시·결과·commit token을 가진 영수증

묶음은 최대 **1 MiB / 2,000행**, 테이블 JSON 256 KiB, 한 행 64 KiB다. 초과하면
부분 성공이나 자동 분할 없이 거절한다. 작은 원자적 이전부터 검증하는 경계이며 대형
자료의 단계적 수입 프로토콜은 지원하지 않는다. 입력 내용은 실행 지시가 아니며 파일 경로를
열거나 스킬 스크립트·검사 명령을 실행하지 않는다.

`importD1Project(binding, bundle, {transfer_id, generation, role})`는 형식·전체 해시·정확한
테이블 목록과 행 스키마, 소유권·작업 범위·정정 관계·결정 그래프·계획·스킬 해시·중단
저장 지점을 검증한다. 빈 목적지에서 FK를 지연 검사하는 **단일 D1 batch**로 가져오고
가져오기 영수증·과거 이벤트 표식·쓰기 차단 권한까지 함께 확정한다. FK를 끄지 않는다.
같은 묶음/이전 ID의 재시도는 저장된 영수증을 재사용하며 다른 내용은 덮어쓰지 않는다.
FTS는 원문 삽입 트리거로 재구성한다. 오류 위치별 전체 롤백은 실제 workerd로 검사한다.

## 쓰기 전환

```ts
const transfer = new D1ProjectTransfer(sourceBinding, emptyTargetBinding, projectId);
await transfer.prepare(transferId, expectedSourceGeneration);
await transfer.activate(transferId);
const writer = withD1Generation(targetBinding, 1); // 실제 status가 반환한 generation 사용
```

위 호출은 호스트 내부 API이며 임의 외부 요청을 승인하는 API가 아니다. 원격 계층은
향후 사용자·프로젝트 권한을 별도로 확인해야 한다. 생성자가 받은 binding 세대는 writer
생성 시 고정하며 AI가 보낸 mutation의 세대로 대체하지 않는다. 관리되지 않은 이전 DB의
기본 세대는 0이다. 정확한 저장소 ID와 이전 ID·프로젝트·세대를 확인한다.

1. 원본의 미종료 실행 관측이 있으면 준비를 거절한다. 실행을 임의 종료하거나 재실행하지 않는다.
2. 원본 제어 행과 프로젝트별 봉인을 같은 batch에 저장한다. 다른 프로젝트는 계속 쓸 수 있다.
3. 원문을 내보내 빈 목적지에 **차단된 사본**으로 가져온 뒤 prepared로 전환한다.
4. 원본에 활성화 의도(activating)를 먼저 확정한 뒤 목적지의 정확한 세대를 연다.
5. 원본은 읽기 가능·쓰기 차단으로 남고 대상만 새 작업을 받는다. 자동 전달은 없다.

이미 열려 있는 원본의 raw statement도 DB 트리거가 막는다. 고수준 writer는 세대 확인과
batch 내부 SQL guard를 함께 사용하여 사전 확인 뒤의 경합도 거절한다. 새 대상에서는
호스트가 `withD1Generation`으로 선택한 세대만 업무 API에 전달한다. 기존 완료 요청의
영수증 재조회는 새 쓰기가 아니므로 유지한다. `claims_verified=false`다.

## 실패·중단 후 복귀

`transfer.recover(transferId, optionalFreshReturnBinding)`을 같은 이전 ID로 명시적으로
다시 호출한다. 단계는 원본 D1에 남고 새 프로세스/연결에서도 이어서 조회할 수 있다.

- **활성화 의도 전:** 대상은 닫고 원본을 새 세대로 다시 연다. 결과는 aborted다.
  오래된 세대의 연결은 원본이 재개되어도 쓸 수 없다.
- **활성화 의도 후:** 원본은 다시 열지 않는다. 대상의 fence 세대를 단조 증가시켜 닫고,
  최신 자료를 새 세 번째 return DB로 가져온다. 원본에 선택된 return store ID를 CAS로
  확정하여 경쟁 복구 중 하나만 열 수 있다. 활성화 후 생긴 작업과 영수증도 보존한다.
- 대상 봉인 세대를 증가시키므로 대기 중이던 과거 activate가 나중에 도착해도 대상을
  다시 열지 못한다. source phase CAS만으로 서로 다른 DB의 원자성을 가장하지 않는다.
- 수입 후 응답만 유실되거나 return을 연 뒤 완료 단계 저장 전에 끊겨도 같은 사본·영수증을
  재사용한다. 목적지 또는 선택된 return의 정체성이 바뀌면 양쪽을 임의 활성화하지 않는다.

불완전하거나 손상된 선택 DB를 자동 삭제/교체하지 않는다. 사용할 수 없는 정본·미종료
실행 관측 등으로 봉인과 최신성을 확인하지 못하면 복구가 차단될 수 있다. 디스크 손실,
여러 저장소의 원자적 장애 복구나 동일 OS 사용자의 직접 SQL 변조까지 보장하지 않는다.
이전에 사용한 원본 제어 행은 유지하며, 같은 원본 프로젝트의 새 이전을 겹쳐 시작하지 않는다.

## 이벤트와 검사 근거

가져온 이벤트·작업 연결은 원문을 보존하고 별도의 `d1_import_origins`로 표시한다.
`linkage=imported_history`, `current_session_binding=false`이며 현재 연결로 자동 재활성화하지
않는다. 새 호스트 이벤트를 받은 뒤 새 명시적 link가 필요하다. 가져온 anchor는 새 link의
근거로 쓸 수 없다. 과거 중단 저장 지점과 최신 저장 지점은 각각 조회한다.

기록이 저장됐다는 영수증, 실제 로컬 D1 동작, 합성 실행 결과, AI 보고는 서로 다르다.
이전은 AI 보고를 직접 실행 관측으로 바꾸지 않는다. 현재 코드 관측기가 없으면 근거는
unknown으로 유지한다. 수신하지 못한 이벤트/기록의 누락 개수와 완전성은 확인하지 못한다.

## 검증

`tests/d1-transfer.test.mjs`는 실제 Miniflare/workerd의 별도 테스트 DB와 새 연결에서
26개 업무 테이블, 정정 이력 FK, 다른 프로젝트 격리, 기존 writer 차단, 가져온 이벤트,
오류 위치별 롤백·응답 유실·activate/recover 교차·경쟁 복구·최신 복귀를 검사한다.
테스트 Worker는 인증된 제품 API가 아니다. 중단/응답 유실은 테스트가 주입한 경계이며
실제 Codex 중지 버튼이나 원격 네트워크 장애를 관측했다고 표시하지 않는다.
