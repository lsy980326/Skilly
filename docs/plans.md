# 계획·체크리스트 진행 관리

계획은 ‘하기로 한 일’, 작업은 ‘실제로 수행한 한 차례의 일’이다. 한 계획 항목에 여러
작업을 연결할 수 있고, 한 작업이 여러 항목을 진행할 수도 있다. 기존 기능별 작업 조회를
대체하지 않는다. 계획은 기능·구성요소와 함께 작업을 찾는 별도의 기준이다.

## 원문과 버전

`memory_save_plan`은 호스트가 전달한 선택된 Markdown 또는 대화 원문과 항목·완료 조건을
저장한다. 파일 경로는 출처 표시용이며 Skilly가 해당 파일을 열거나 바꾸지 않는다.
전체 폴더를 감시하지 않고, 일반 작업일지를 MD로 만들지 않는다.

- `plan_key`는 프로젝트·저장소·환경 안에서 고정된 계획 이름이다.
- `expected_version: 0`으로 첫 버전을 만들고, 이후에는 조회한 최신 버전을 지정한다.
  서로 다른 세션이 같은 버전을 바탕으로 수정하면 충돌로 알리고 덮어쓰지 않는다.
- 원문·항목·완료 조건을 바꾸면 새 불변 버전을 추가한다. 이전 버전과 진행 이력은 보존한다.
- 항목 `key`와 완료 조건 `key`는 해당 버전 안에서 고정한다. 의미가 바뀐 새 버전으로
  이전 완료 보고나 검사 연결을 자동 승계하지 않는다.
- Markdown의 `- [ ]`, `- [x]`, 번호형 체크리스트는 `items` 생략 시 항목으로 변환한다.
  fenced code 안의 체크리스트는 제외한다. 계층 들여쓰기는 첫 버전에서 평탄화한다.
  체크 표시 자체는 `source_checked`로 보관하고 진행 상태는 모두 시작 전이다.
- 대화 계획에는 AI가 명시적인 항목과 완료 조건을 전달한다. 일반 문서의 설명을 서버가
  임의로 계획 항목으로 해석하지 않는다. 기존 문서 가져오기와 계획 등록은 별도 요청이다.

## 작업·완료 조건·근거 연결

`memory_update_plan_item`은 현재 활성 작업의 저장된 보고 `record_id`와 항목 상태를 연결한다.
새 이력만 추가하며 기존 보고·작업·MD를 수정하지 않는다. 같은 프로젝트·저장소·환경·작업의
보고만 연결할 수 있다. 항목에 구성요소나 기능을 지정했다면 작업에도 같은 연결이 있어야 한다.

상태는 시작 전(`pending`), 진행중(`in_progress`), 막힘(`blocked`), 완료 보고(`completed`)다.
완료 보고에는 모든 완료 조건에 대한 `criteria_results`의 충족 보고와 설명이 필요하다.
소급 또는 정정된 보고로 새 완료를 선언할 수 없다. 나중에 연결 보고가 정정되면 해당 항목은
다시 확인(`needs_review`)으로 표시하고 완료율에서 뺀다. 작업 종료 자체로 항목이 완료되지는 않는다.

조회한 `update_id`를 다음 쓰기의 `expected_update_id`로 전달한다. 첫 갱신만 null이다.
다른 세션이 그 사이 바꿨다면 충돌로 반환한다. 저장 실패 시 원래 입력·멱등 키로 재시도한다.
계획 쓰기는 일반 작업 보고용 복구 보관함에 자동 대기하지 않는다.

직접 검사 근거는 `execution_ids`로 명시 연결한다. 반드시 같은 작업의 실행 관측이어야 한다.
검사 개수와 성공·실패, 현재 코드와의 비교는 실행기가 수집한 값으로 읽는다.
AI의 완료 조건 충족 보고와 직접 검사는 서로 다른 축이다. 통과한 검사 하나가 항목 전체의
완료 조건이나 배포를 증명하지 않으며 `claims_verified`는 false로 유지한다.

## 진행률과 조회

`memory_query_plans`는 기본적으로 범위 안의 최신 계획 목록을 반환한다. `plan_key`를 주면
선택 버전의 원문, 항목, 완료 조건, 마지막 갱신 ID, 연결 작업·보고·직접 검사 근거를 읽는다.
`remaining_only: true`는 완료 보고가 없는 항목만 반환하지만 진행률 분모는 전체 필수 항목이다.

진행률은 **필수 항목 완료 보고 수 / 필수 항목 수**다. 선택 항목은 별도 수로 표시한다.
항목 수 기반이며 작업량·시간 추정치가 아니다. 모든 필수 항목에 완료 보고가 있어야 계획을
`completed_reported`로 표시한다. 필수 항목이 없으면 100%나 완료로 표시하지 않는다.
판정 불가, 막힘, 미시작은 완료에 포함하지 않는다.

화면은 기존 프로젝트의 **계획** 탭에서 목록·진행률·남은 항목·완료 조건·원문·버전을 조회한다.
항목의 **연결 작업 보기**로 기존 작업 상세에 이동한다. 화면은 조회만 하며 등록·진행 기록은
일반 작업 AI가 MCP와 스킬로 수행한다. 화면과 MCP는 같은 읽기 모듈과 계산을 사용한다.

상세의 `linked_tasks`는 **선택한 계획 버전의 진행 이력에 명시 연결된 작업**을 모은다.
이름·저장된 상태·작성자·관련 항목·연결 보고 수를 표시하고 누르면 작업 상세로 이동한다.
항목별 최신 진행 작업도 이름과 함께 표시한다. 다른 작업이 같은 항목을 이어 진행해도
앞선 작업은 이 목록에 남는다. 계획을 등록만 한 작업이나 제목이 비슷한 작업은 자동 연결하지 않는다.
최근 연결 순으로 최대 20개와 전체 수·생략 여부를 반환하며 다른 버전·범위의 연결을 섞지 않는다.
작업의 미완료/종료 상태는 저장된 기록이지 실시간 실행·항목 검증 완료를 뜻하지 않는다.

## 한 사이클

1. 사용자: ‘이 MD/대화 계획대로 기능을 구현해줘.’
2. AI: 프로젝트·기록 조회, 활성 작업 시작. 허용된 원문만 읽어 계획 등록 또는 기존 계획 조회.
3. AI: 선택 항목의 완료 조건과 기존 근거를 확인하고 작업·구성요소·기능을 연결.
4. AI: 변경 보고를 저장한 뒤 진행 항목을 갱신. 허용된 검사는 기존 실행기로 수집.
5. AI: 항목별 완료 조건의 충족/미충족을 보고하고 실제 실행 ID를 별도로 연결.
6. 다음 작업: 계획 검색과 남은 항목 조회 후 새 작업으로 이어감. 이전 세션을 임의 종료하지 않음.

## 저장과 제한

DB v11의 `plan_versions`, `plan_item_updates`, `plan_update_executions`에 추가 저장한다.
기존 작업·원문·영수증은 보존한다. 쓰기·영수증·프로젝트 revision 증가는 같은 트랜잭션이다.
구버전 DB의 읽기 화면은 빈 계획 목록과 `schema_supported: false`를 반환하며 마이그레이션하지 않는다.
전체 백업과 프로젝트 사본 교환에 원문·버전·진행·연결 근거를 포함한다. 가져온 검사 근거는
원래 출처를 보존하지만 새 컴퓨터의 검증 완료로 승격하지 않는다.

원문은 최대 24,000자이자 48 KiB, 버전당 항목 20개, 항목당 완료 조건 4개,
진행 갱신당 실행 연결 4개다. 목록은 최대 20개씩, 상세 버전 목록은 최근 20개를 표시하고
더 이전 버전도 번호로 직접 조회할 수 있다. 원문·명령 문자열은 데이터이며 실행하지 않는다.
