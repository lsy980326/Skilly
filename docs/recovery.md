# 중단·저장 실패 확인과 복구

Skilly는 작업 시작·변경·마감 요청을 로컬에 보관한 다음 기록 DB에 저장한다.
DB 잠금이나 연결 중단 뒤에는 보관된 요청을 다시 처리할 수 있다. 실제 명령·전체
대화·파일 변경을 관찰하는 기능은 아니다. 서버에 도착하지 않은 요청은 복구할 수 없다.

## 누락 감지의 경계

MCP와 화면의 `delivery_status`는 같은 영수증·보관 입력 기준을 사용한다.
기존 `persistence`와 `recovery_state`/화면 `state`는 호환성을 위해 유지한다.

| 전달 상태 | 의미 |
|---|---|
| `saved` | 같은 입력의 본 DB 저장 영수증이 있음. 보고 내용이 사실이라는 뜻은 아님 |
| `recovery_pending` | 원래 입력이 보관됨. 저장은 미확인이고, 현재 작업에 허용된 요청만 영수증 확인 후 재시도 |
| `recovery_blocked` | 입력은 있지만 충돌·도메인 거절 등 확인이 필요함. 키 변경·자동 우회 금지 |
| `not_retained` | 영수증도 보관 입력도 확인되지 않음. 원래 요청 재생을 꾸며내지 않음 |

`recording_coverage`는 이 연결이 서버에 도착한 요청의 영수증과 보관 입력만
관측한다고 명시한다. `missing_record_count: null`, `completeness: unknown`은
누락 수를 측정할 수 없다는 뜻이다. 빈 목록, 오래된 `active`, 서버 재시작만으로
누락 0건·작업 중단·현재 실행 상태를 판정하지 않는다. 본 DB 자체를 읽을 수 없으면
조회가 실패하며, 실패 응답을 저장 확인이나 빈 정상 결과로 해석하지 않는다.

## Codex 실행 이벤트 지원 확인

[공식 Hooks 문서](https://learn.chatgpt.com/docs/hooks)를 2026-10-21에 확인했다.
설치된 CLI `0.144.4`의 `codex features list`도 `hooks stable true`를 표시했다.
이는 지원 가능성 확인이며 이 저장소에 훅이 설치·관측됐다는 증거는 아니다.

- 세션 시작·턴 종료·사용자 중단과 로컬 도구 실행 전후 이벤트가 문서화되어 있다.
- 실행 전후 이벤트는 모든 경로를 감싸지 않으며, 강제 종료는 정상 종료 이벤트와 다르다.
- 프로젝트 신뢰와 개별 훅 정의의 신뢰 검토가 필요하다. 설정이 있어도 미승인 훅은 건너뛸 수 있다.
- 세션 시작 시 MCP 준비가 끝나지 않을 수 있고, MCP 훅이 연결을 대신 재시작하지는 않는다.

선택적 훅 후보와 최소 이벤트 수집은 [Codex 실행 이벤트 안내](codex-lifecycle.md)를 따른다.
기존 설정에는 자동 설치하지 않는다. 이벤트 저장과 작업 기록 영수증은 별개다.
아래의 기존 복구 검증은 사용자 설정·신뢰를 바꾸지 않고
로컬 MCP 요청, DB 잠금 실패, 테스트 서버 강제 종료,
새 연결에서 영수증 재확인과 원래 요청 재시도를 대상으로 한다. 이를 Codex가
일반 작업의 모든 이벤트를 자동 수집한 결과와 혼동하지 않는다.

별도 명시적 실행기 `skilly exec`의 프로세스 관측은 [실행 결과 수집](execution-results.md)을 따른다.
일반 훅 이벤트와 구분하며 종료 저장이 실패한 실행 결과는 원래 입력 보관 큐로 자동 복구되지 않는다.

## AI가 사용하는 순서

1. 기존처럼 프로젝트를 식별하고 이전 기록을 조회한다.
2. 새 세션 시작 또는 재연결 시 `memory_recovery_status`를 한 번 조회한다.
3. 현재 요청과 관련된 보관 요청이 있으면 저장 영수증부터 확인한다.
4. 사용자가 허용한 작업의 원래 요청 한 건을 `memory_retry_write`로 재시도한다.
5. `persisted` 응답의 작업·기록 ID를 확인한 뒤 작업을 이어간다.

재시도는 보관된 도구·입력·키를 그대로 사용한다. DB에 이미 영수증이 있으면 기존
결과를 반환하므로 응답 유실을 새 기록 생성으로 처리하지 않는다. 시작 요청이 저장되지
않았던 경우에도 같은 시작 요청을 처리한다. 코드 수정은 시작 저장 확인 이후에 한다.
다른 세션의 열린 작업을 임의로 인계하거나 종료하지 않는다.

`use-skilly`가 이 절차를 안내하므로 사용자가 매번 복구 명령을 쓸 필요는 없다.
다만 실행은 AI의 지침 수행에 의존하며 자동 재생 루프나 상주 감시기는 없다.
“이번에는 기록하지 마”라는 요청은 보관 요청 재시도도 금지한다.

## 상태를 읽는 방법

| 표시 | 실제 의미 | 다음 행동 |
|---|---|---|
| 작업 `active` | 시작은 저장됐지만 종료가 저장되지 않음 | 진행 중인지 중단됐는지 작업 맥락으로 확인 |
| 작업 `interrupted` | 중단 보고와 함께 마감함 | 보고와 현재 코드 확인 후 새 작업 시작 |
| 요청 `persisted` / `saved` | 같은 입력의 실제 DB 영수증이 존재함 | 기존 작업·기록 ID 사용 |
| `not_found` / `retry_required` | 조회 시점에 영수증이 없고 원래 입력이 보관됨 | 허용된 해당 작업만 그대로 재시도 |
| `unconfirmed` | 요청은 보관됐으나 처리 결과가 불분명함 | 영수증 확인 후 동일 요청 재시도 |
| `blocked` / `conflict` | 닫힌 작업, 충돌 등의 이유로 원래 요청을 적용할 수 없음 | 원문을 바꾸거나 새 키로 자동 우회하지 않음 |
| `rejected` | 잘못된 새 요청이 확정적으로 거절됨 | 오류를 고친 별개의 요청으로 처리 |
| `payload_unavailable` | 원래 입력이 없음 | 재시도를 꾸며내지 않고 필요 시 별도 소급 보고 |

`active`의 경과 시간만으로 실패·중단을 선언하지 않는다. 상태 조회는 작업 종료나
재시도를 수행하지 않는다. 기록 내용은 여전히 `agent_report / unknown`이다.
`completed`와 `persisted`는 코드·테스트의 정확성을 보증하지 않는다.

## 당시 보고와 소급 보고

변경 및 종료 도구에는 선택 입력 `report_origin`이 추가됐다.

| 값 | 표시 |
|---|---|
| `contemporaneous` | AI가 해당 작업 중 작성했다고 선언한 보고 |
| `retrospective` | 나중에 재구성한 소급 보고 |
| `unspecified` | 작성 시점이 지정되지 않은 보고 |

기존 기록은 `unspecified`로 유지한다. 본문에 “소급”이 있다는 이유만으로 자동 분류하지
않는다. 원래 보관 요청의 재시도는 입력과 분류를 그대로 유지한다. 저장 시각은 실제
DB 저장 시각이며, 복구 보관소의 `first_received_at`은 서버가 처음 보관한 시각이다.
직접 관측 시각을 명시한 요청은 그 값을 그대로 보존한다.

원래 요청이 없어서 새로 정리한다면 새 작업에서 `retrospective`로 기록하고, 알려진
이전 작업 ID와 직접 확인한 근거를 본문에 구분해 적는다. 빠진 시작·종료 이벤트를
과거 시각으로 만들지 않는다. 이 분류도 AI의 선언이지 자동 실행 증거가 아니다.

## 사용자 확인

Skilly 폴더에서 현재 DB의 미완료·중단 작업과 보관 요청을 읽기 전용으로 확인한다.

```sh
npm run memory:inspect -- \
  --project /Users/yeop/project/plamingo_review/flamingo-review-web \
  --db /Users/yeop/project/Skilly/.skilly/memory.sqlite \
  --attention
```

`--attention`을 빼면 최근 작업을 표시한다. `--run UUID`는 해당 작업만 표시하며,
아직 작업 ID가 생기지 않은 시작 요청은 이 필터에서 제외된다. `--limit 20`과
`--json`도 사용할 수 있다. 조회 자체는 DB나 복구 보관소를 만들거나 이전하지 않는다.
MCP 상태 조회는 `limit`·`offset`과 `next_offset`으로 다음 항목을 볼 수 있다.
동시에 작업이 바뀔 수 있으므로 목록 전체가 고정된 한 시점의 스냅샷은 아니다.

AI에게는 “이 프로젝트의 미완료 작업과 저장 실패를 읽기 전용으로 확인해줘”라고
물으면 된다. 이어가려는 작업이 명확하면 “방금 실패한 저장 요청을 원래 입력 그대로
복구하고, 저장 ID와 소급 여부를 알려줘”라고 요청할 수 있다.

## 보관·호환성·한계

- 본 DB가 `memory.sqlite`이면 복구 보관소는 `memory.sqlite.recovery.sqlite`다.
  동일 폴더의 별도 SQLite 파일이며 새 파일 권한은 소유자 전용 `0600`이다.
- 작업 요청만 보관하며 등록·읽기·임의 도구 호출은 보관하지 않는다. 등록/범위 확인
  자체가 실패하거나 서버가 요청을 받기 전에 끊기면 보관을 주장하지 않는다.
- 미해결 원본 입력은 DB 전체 합계 **100건 / 1 MiB**로 제한한다. 한도나 보관 오류가
  발생하면 본 DB 쓰기를 시도하지 않고 알린다. 유실된 요청을 저장됐다고 표시하지 않는다.
- 성공하면 본 DB의 기록·영수증을 보존하고 복구 보관소의 중복 입력 본문만 비운다.
  요청 ID·해시·시각 메타데이터는 남기므로 재호출로 기존 영수증을 확인할 수 있다.
- 새 요청의 확정적 도메인 거절은 오류·해시만 남기고 재시도 용량을 점유하지 않는다.
  이미 실패로 보관했던 입력이 나중에 막히면 그대로 남는다. 막힌 원본의 처분·보존
  정책은 별도 후속 기능이며 무한 재시도나 임의 삭제를 하지 않는다.
- 본 DB가 저장됐지만 보관소 확인에 실패하면 `persisted`와
  `journal_acknowledged: false`를 함께 반환한다. 보관소에 없는 기존 영수증은
  `request_id: null`이며, 없는 복구 요청 ID를 만들어 주지 않는다.
- 새 런타임이 본 DB v1을 v2로 트랜잭션 이전한다. 기존 본문·시각·ID·영수증을
  보존하고 분류 열과 작업 조회 인덱스만 추가한다. 이전 후에는 v2를 지원하는
  런타임을 사용해야 하며 오래된 실행 파일로 되돌리는 자동 다운그레이드는 없다.
- 기존 연결의 새 도구 목록은 자동 갱신되지 않을 수 있다. 최신 빌드와 스킬을 적용하고
  연결을 다시 열어 `memory_recovery_status`와 `memory_retry_write` 노출을 확인한다.
  다른 프로젝트의 설정·설치 스킬은 이 소스 변경만으로 덮어쓰지 않는다.
- 로컬 사용만 지원한다. 두 파일을 함께 안전하게 백업·이전하는 제품 기능, 자동 명령
  수집, 과거 작업 전체의 무누락 판정, 검증 상태 자동 승격은 이번 범위에 없다.

## 2026-10-21 확인 범위

아래는 당시 시험 조건과 결과를 보존한 이력이다. 끝의 “현재 데스크톱 채팅”도
그 시험 시점을 가리킨다. 오늘 사용하는 채팅의 연결이나 자동 복구 성공 여부는
그 채팅의 실제 저장 영수증과 재조회로 별도 확인한다. 최신 구현·미검증 범위는
[로컬 지원 안내](development.md#현재-로컬-기능과-확인-범위)를 따른다.

| 구분 | 직접 확인한 결과 |
|---|---|
| `npm test` | 40/40 통과. 잠금 실패, 프로세스 재시작, 영수증 재사용, 큐 상한, 범위 격리, 동시 재시도, v1 이전 포함 |
| 실제 stdio MCP 시험 | 임시 DB에서 서버 프로세스를 다시 열고 변경·마감 요청 복구, 중복 기록 없음. 자동 테스트의 일부 |
| 설치 설정 연결 검사 | `verify-codex.mjs --configured`로 새 Codex 프로세스 2개에서 9개 도구와 복구 도구 노출 확인. 네트워크 차단·모델 실행 0회 |
| 사용자 DB 보존 | 로컬 백업 후 v1→v2 확인. 기존 기록 본문 등 불변 필드 49건과 저장 영수증 75건 일치, 외래 키·quick_check 정상 |
| 스킬·문서·리뷰 | 스킬 유효성 검사, 로컬 링크 대상 40개, diff 검사 통과. 독립 검토 지적 수정 후 재검토 완료 |

현재 데스크톱 채팅의 도구 목록 갱신과 실제 사용자 작업에서 AI가 스스로 실패를
발견·복구하는 행동은 위 연결 검사로 검증하지 않았다. 설치된 실제 서버의 DB
경로를 개인 설정에서 읽어 확인하지 않았으며, DB 보존 검사는 지정된 로컬 DB에서
별도로 수행했다. 저장 내용의 검증 상태는 승격하지 않았다.
